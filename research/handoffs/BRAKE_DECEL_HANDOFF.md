## State of knowledge (established, high-confidence)
- **Two engine ACC channels, both fully mapped:** (A) torque PI `801e9b86` → `d000e2xx`; (B) accel/decel
  **demand** `801e6df0` (cal `0x80079940`, clamp **+1.64 / −0.82 m/s²**) → `d9e4 → 801df324 → d0007b68 →
  80141904` (engine setpoint). Channel B is the engine's OWN (weak) braking authority.
- **DECISIVE (UPDATE 46, complete a0-relative scan of `d000d900-da54`):** the engine ACC RAM contains **NO
  brake-decel channel** — nothing writes a −3.0-style value or reaches a TSK/CAN packer. So `TSK_Verzoeg_Anf`
  is NOT computed in the engine's internal ACC subsystem. It is **relayed into TSK_02 with the clamp applied
  at the Com-pack step**, or enforced by the ESP.
- **−600 (−3.0 @ 0.005 m/s²/bit) exists ONLY in the curve `0x8004dda6`/`0x8004ddb6`** (func + monitor copies,
  tuner-invariant). No scalar −600 in any ACC cal struct. `TSK_Verzoeg_Anf`'s wire value is **raw 41**, a
  different encoding — so don't hunt −600 on the wire signal; hunt it as the internal value or the curve.
- **Com/TSK architecture:** config root `DAT_d0000cd0=0x800906fc` {count=6, PDU_desc@+4=0x80090654,
  handle_tbl@+8=0x80090710, runtime_state@+0xc=0xc0002798, buf_desc_array@+0x10=0xc0002810}. Per-conn signal
  buffer = `0xc0002810 + conn*8`. **TSK_02 = connection 3 → buffer `0xc0002828`.** `canmo_10c_TSK_02@0x801d2956`
  → `com_process_ipdu(3)` (=`0x800af8bc`, which is the **ISO-TP** engine — a misnomer for the periodic path).
  Com_SendSignal = `801cf11a` (← `801240a0`), dispatched indirectly through the runtime context
  `_DAT_c03fc37c`. The generic Com per-signal pack (`com_ipdu_process_step@0x8002523c` via `_DAT_c03fc37c`)
  reads the signal from the runtime buffer — the "Com wall" (only materializes when the cyclic Com main runs).

## THE KEY TOOLS (use these — they broke the "computed-pointer wall")
The ACC subsystem addresses RAM **a0-relative** (`a0=0xd0008000`; `st.h [a0]0x59e4` = write `d000d9e4`).
`getReferencesTo` (absolute xref) MISSES these — which caused years of false "computed-pointer / invisible
writer" conclusions. Two ways to see them now:
1. **`core/ghidra/FindRefsTo.java` — UPGRADED.** Adds a `SymbolicPropogator` pass (seeded by SetBaseRegs'
   a0/a1/a8 context) that resolves each ld/st's effective address (direct base+disp AND lea/addsc.a-propagated)
   and matches the target, printing `[sym] READ/WRITE + function` beside the old `[refdb]` pass.
   - `FindRefsTo <addr1> [addr2 ...]` — per-address writers/readers (scans all 7475 fns once; ~2-4 min).
   - `FindRefsTo 0xLO 0xHI --range` — **map an entire RAM region's** a0/a1-relative accesses in one pass.
   - `--refdb-only` restores the old behavior. Validated: `FindRefsTo 0xd000d9e4` refdb=readers only,
     `[sym]`=WRITE in `801e6df0`. Only the bracketed memory operand is evaluated (no ld.a/st.a false hits).
2. **decompile-grep:** the decompiler resolves a0-relative accesses to `DAT_d000xxxx`, so
   `grep -rlE 'd000XXXX =' decompiles_r/` finds a0-relative WRITERS the reference DB can't.
Other tools: `ScanCalIndexed.java` (per-fn SymbolicPropogator for cal-window reg values),
`DecompileAddrs.java <outDir> <addr...>`, `CoverageStat.java`, `maps/harvest_functions.py` (recover more
functions from CALL-target harvest), `EmulComWatch.java`/`EmulComWatch2.java` (Com-init emulation + invoke).
