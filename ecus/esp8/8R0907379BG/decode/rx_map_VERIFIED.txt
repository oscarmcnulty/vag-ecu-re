## §1  Emulation attempt — VERDICT: init does not materialize a dumpable table
- Stubbed the RTOS allocator (FUN_000a29dc/a2a3c/a11ee — handle-based, uses LR-relative
  computed dispatch `(*(code*)((in_lr&~3)+0x5fc))()`) with a bump allocator and ran the three
  COM-init orchestrators (FUN_0006bb22, FUN_000892a0, FUN_0006b936) under Unicorn.
- All ran to completion but wrote ONLY small queue-state fields (0x4069d0-0x4069e7), NOT the
  0x40a1a8 descriptor table. The real table-builder is reached THROUGH the allocator/handle
  path (which had to be stubbed) and is not one of the reachable orchestrators.
- Confirmed from the static side too: the ACC_10 decel signal 0x405462 has NO static writer —
  it is deposited by the runtime COM routing at a computed address. So neither emulation
  (of the orchestrators) nor static xref yields the per-ID {message->buffer} routing table.
- To materialize it would require faithfully emulating the entire COM/PDU init tree incl. the
  handle allocator with LR-relative trampolines — out of scope / high risk, low incremental
  value for the openpilot goal (the brake path is fully traced, §3).

## §4  RX signal-buffer identification (method + partial list)
RX signal buffers have the signature: READ by consumer fns, NO static writer (COM deposits them
by computed address). This DISTINGUISHES real RX buffers from work/filter vars (which have a
static RMW writer). Enumerated for 0x405400-0x405fff: 259 such buffers. Notable:
  0x405462-66  ACC_10 decel signal (readers FUN_0001ef4c,25c88,2de5c,3488c) -> §3
  0x40542c-5a  (readers FUN_00012590,2a9b8,35d24,43228) large multi-signal block
  0x40550e-18, 0x4055ba-ca, 0x4055e8-ef, 0x4055fa-60c  conditioned RX signal blocks (ANB/ESP inputs)
  0x405d1b-30  decel-source status block (-> decel_src_status_gateway 0x9d9f8)
  0x405e42-ebd TX signal storage (readers=com_signal_compose) — ESP_05 @0x405e81 lives here (TX)
NOTE: this signature IDs RX *storage* but does NOT attribute each buffer to a CAN ID — that link
is the runtime routing (§1) which is not statically recoverable. Per-ID attribution requires a
per-consumer trace (as done for ACC_10 in §3) for each message of interest.
